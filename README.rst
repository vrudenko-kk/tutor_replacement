Поиск и согласование временных замен преподавателей
==================================================

Проект рассчитывает назначения, объясняет отбор и проводит заявку через
согласование до статуса «Подтверждена». Реализован на Python 3.10+ средствами
стандартной библиотеки. Установка сторонних Python-пакетов не требуется.
Используется системная база часовых поясов IANA (обычно доступна в macOS/Linux).

Быстрый запуск
-------------

Откройте терминал в папке проекта, где находится этот файл::

    python3 -m substitution demo
    python3 -m unittest discover -s tests -v

Демонстрация использует учебные данные из examples/scenario.json и приводит
заявку из двух пар к confirmed. Время в ней задано явно, поэтому демонстрация
работает независимо от текущей даты. Все имена и расписание в примере условные.

Подбор по собственным данным::

    python3 -m substitution plan examples/scenario.json --output result.json

Результат содержит assignments, ranked, stage, complete, cost и audit.
complete=false означает, что все пары закрыть не удалось. Частичное решение
в assignments служит для анализа; сервис не подтверждает по нему всю заявку.
Команда plan только рассчитывает решение: она не создаёт предложений и не
назначает замещающих. Текущее время не проверяется при таком расчёте архивных
или моделируемых задач. Сервис проверяет сроки при действиях согласования.

Экран подбора в браузере
------------------------

Из корня проекта запустите::

    python3 -m substitution web

Откройте http://127.0.0.1:8765. Если порт занят, укажите другой через
``--port 8766`` и откройте адрес из терминала. Сервер завершится по Ctrl+C.

Экран сразу рассчитывает учебную заявку. Можно загрузить свой JSON того же
формата, что и examples/scenario.json, повторить расчёт, сравнить кандидатов,
посмотреть причины отсева и скачать результат. Пары в таблице пока только
предложены алгоритмом. Согласование демонстрируется командой
``python3 -m substitution demo``.

В оформлении использованы цвета, сетка и варианты логотипа из брендбука
Финансового университета (стр. 8, 15–16, 40–46). Open Sans поставляется
локально по лицензии SIL OFL. Для заголовков используется установленный
Book Antiqua или Palatino при его отсутствии. Шрифты, логотипы и интерфейс
работают без внешних сетевых запросов.

Сохранённые заявки
-----------------

Создайте новую базу, подайте учебную заявку и начните подбор::

    python3 -m substitution init examples/scenario.json --database schedule.sqlite
    python3 -m substitution action examples/create.json --database schedule.sqlite
    python3 -m substitution action examples/start.json --database schedule.sqlite
    python3 -m substitution snapshot --database schedule.sqlite
    python3 -m substitution audit --database schedule.sqlite

init импортирует справочники и расписание; заявка подаётся отдельным действием.
Повторный init существующей базы запрещён, чтобы не затереть состояние.
Для реальной работы замените учебные даты. Поле now в примерах — моделируемое
время; в рабочем приложении не передавайте его, чтобы использовались часы сервера.

В snapshot найдите id предложения и teacher. Сохраните такой JSON в interest.json,
подставив реальные идентификаторы, затем выполните команду action::

    {
      "method": "interested",
      "arguments": {
        "offer_ids": ["идентификатор_предложения"],
        "actor": {"id": "anna", "role": "teacher"}
      }
    }

Для окончательного согласия вызовите action с теми же данными и method="take".
Несколько предложений одной заявки одному преподавателю можно передать одним
списком: блокировка и принятие пакета атомарны. Для отказа используется decline
с единственным offer_id. Тестовые действия должны передавать одинаковую
временную шкалу now, как examples/create.json и examples/start.json.

Обработка таймаутов::

    {"method": "poll", "arguments": {}}

В рабочем приложении вызывайте Service.poll() периодически, например раз в
30 секунд. Собственный фоновый процесс проект не запускает. Без poll() состояние
таймаутов в экспорте не меняется само; операции ответа также проверяют сроки.
Ошибочная операция откатывается целиком, включая выполненную внутри неё проверку
сроков: следующий poll() зафиксирует истечения независимо от ошибочного ответа.

Использование как библиотеки
---------------------------

Пример расчёта::

    import json
    from substitution import Dataset, Planner, Request

    with open("examples/scenario.json", encoding="utf-8") as file:
        source = json.load(file)
    data = Dataset.from_dict(source["data"])
    request = Request(**source["request"])
    result = Planner(data).plan(request)

Пример запуска согласования::

    from substitution import Actor, Service

    secretary = Actor("secretary-1", "secretary", "informatics")
    service = Service("new.sqlite", data)  # При повторном открытии data не передавать.
    service.create(request, secretary)
    service.start(request.id, secretary, mode="parallel", timeout_minutes=20)
    service.close()

У Actor есть id, role и department. Это доверенный контекст, который реальное
приложение получает после аутентификации. CLI и библиотека не являются публичным
сервером аутентификации. Нельзя позволять внешнему пользователю произвольно
выбирать actor или now. snapshot() и audit() — административные экспорты.

Что реализовано
---------------

* Проверка дат, кафедры и периода работы, уровня ПСЗ, компетенций, явного отказа,
  светофора, площадки, расписания, лимитов и исторического запрета.
* Классификация окон, направленная матрица времени переездов и проверка пути
  до и после замены, включая другие назначенные замены и резервы.
* Минимальная стоимость максимального потока с девятью признаками и настраиваемыми
  весами; последовательная эскалация при невозможности полного назначения.
* Рейтинг для каждой пары с оценкой возможности закрыть остальные пары заявки.
* Последовательное и параллельное согласование, таймауты, пакетные ответы,
  блокировки «Заинтересован», отзыв конкурентов только по принятой паре.
* Повторный подбор после отказа и таймаута с исключением отказавшихся кандидатов.
* SQLite, аудит решений, очередь уведомлений и лента сообщений без уведомлений.
* Решения секретаря: условия онлайн, повышение лимита, снятие исторического
  запрета для конкретной заявки, ручное назначение, выделение подзаявки, отмена.
* Приоритет замещающих первого дня одного эпизода отсутствия через episode_id.

Статусы заявки: submitted («Подана»), searching («В подборе»), negotiating
(«Согласование»), confirmed («Подтверждена»), failed («Провалена»), cancelled
(«Отменена»). Дополнительный внутренний статус manual_required означает ожидание
ручного решения. Черновик находится на стороне вызывающего приложения; сервис
создаёт поданную заявку. Документооборот после подтверждения не реализован,
как и предусмотрено текущей целью исходного документа.

Статусы предложения: proposed, interested, taken, declined, timeout, withdrawn.
Принятые пары остаются назначенными, даже если поиск остальных завершился
неудачно. Вся заявка при этом не становится confirmed. Секретарь может выделить
незакрытые пары в подзаявку; тогда полностью закрытый остаток подтверждается.
Отмена заявки с уже принятыми заменами запрещена до такого выделения.

Алгоритм и его границы
---------------------

Граф: S → преподаватель → (преподаватель, слот) → пара → T. Дневные остаточные
лимиты задаются на первом ребре, ёмкость слота и пары равна единице. Отрицательные
стоимости допустимы: поиск увеличивающего пути использует Bellman–Ford.

Граф из документа не связывает две разные замены одного преподавателя по
времени переезда. Поэтому после потока проверяется последовательность его
занятий. Для конфликтующих назначений задача ветвится: запрещается одно либо
другое назначение, поток пересчитывается. Очередь ветвей упорядочена сначала
по максимальному покрытию, затем по минимальной стоимости. Первое совместимое
решение оптимально среди сформированных допустимых рёбер с точностью целочисленной
стоимости. На базовых ступенях запрещён и переезд между новыми заменами.

Для рейтинга каждое допустимое назначение по очереди фиксируется, а остальные
пары оптимизируются заново. Сортировка: больше закрытых пар, меньше суммарная
стоимость, меньше индивидуальная стоимость, код преподавателя. Последовательный
опрос начинается с кандидатов найденного совместимого оптимального назначения;
это также разрешает неоднозначность равных оптимальных решений. В параллельный
пул попадают только кандидаты, которые по отдельности допускают полное закрытие.
Комбинация их последующих ответов может потребовать нового подбора или эскалации.

Один расчёт потока требует порядка F·V·E операций, где F — число пар, V и E —
размеры графа. Ветвление по переездам в худшем случае экспоненциально, а полный
рейтинг вызывает оптимизатор для каждого допустимого ребра. Предел
max_search_nodes=20000 действует на один запуск оптимизатора. При превышении
выдаётся SearchLimit / manual_required, а не ложное заключение о невозможности.
Общего лимита времени на все расчёты рейтинга пока нет. Для больших вузов нужны
нагрузочные измерения, ограничение пула, фоновые задачи и оптимизация хранилища.

Переезды считаются непосредственными между соседними занятиями по заданной
матрице; неизвестное направление недопустимо. Ожидается, что матрица содержит
реальное минимальное время пути. Стоимость кандидата вычисляется относительно
сохранённого расписания и резервов на момент подбора. Стоимость окна не
пересчитывается динамически от ещё не принятых назначений внутри решения.

Принятые трактовки неоднозначностей документа
------------------------------------------

1. «Общий» не требует компетенции уже на базовом шаге согласно разделу 6.5.
   Ступень GENERAL сохранена в аудите как повторная проверка без ослабления.
   Явный «Отказ» по целевой дисциплине остаётся запретом.
2. Жёлтый допускается с третьей ступени эскалации. Отсутствие светофора
   трактуется как жёлтый. Policy.yellow_at_base=True позволяет альтернативное
   прочтение. Красный не снимается автоматически.
3. Для смежного уровня точное владение тоже подходит. Если у целевой дисциплины
   нет групп смежности, на ALL_RELATED достаточно любой другой разрешённой
   компетенции. Дисциплинарный уровень не ослабляется.
4. Желательность площадки преобразуется в штраф 1 − вес_площадки. Иначе знак
   формулы минимизации предпочитал бы менее желательную площадку. Вес 0 — запрет.
5. Численные веса и шкалы признаков в исходнике не определены. В проекте заданы
   демонстрационные значения; администратор может заменить все девять весов.
   Все признаки лежат в [0,1], сумма нормируется на сумму весов и умножается
   на 1 000 000 с округлением до целого. History и preference вычитаются.
6. Приоритет окна: inner_gap=0, adjacent=0.25, full_day=0.5, outer_gap=0.75,
   cross_campus=1. Есть занятия с обеих сторон на нужной площадке — inner_gap;
   иначе непосредственное соседство по сетке — adjacent. Подтверждённые замены
   и резервы учитываются как занятость при последующих расчётах.
7. comp_level: priority=0, ready=1/3, prepare=2/3, нет компетенции=1.
   psz_mismatch: точная компетенция=0, смежная=0.5, без неё=1.
   campus_priority весит 6, window_priority — 2; площадка обычно важнее окна,
   но это взвешенная сумма, а не безусловная лексикографическая сортировка.
   travel_penalty=min(минуты_переезда/120, 1).
8. История — среднее всех доступных оценок по тройке до даты замены включительно;
   без истории — 3. Любой неистёкший ноль блокирует независимо от среднего.
   Запрет истекает в календарную годовщину даты записи; 29 февраля переходит
   в 28 февраля. Снятие запрета не удаляет исходную оценку и действует на заявку.
9. consecutive_priority=0 для замещавшего в первый день указанного episode_id,
   иначе 1. В standalone Planner список preferred передаётся явно. Service
   дополняет его по принятым заменам предыдущих заявок того же эпизода.
10. Таймаут отсчитывается от отправки предложения. «Заинтересован» не продлевает
    его. На границе expires_at предложение уже истекло. Срок ограничен deadline.
11. Резерв «Заинтересован» занимает и слот, и дневной лимит. Пакет сначала целиком
    проверяется, затем целиком сохраняется. Повторное принятие не идемпотентно:
    оно возвращает ошибку, не создавая дополнительной замены.
12. Онлайн не применяется без online_allowed у занятия и явно заданного
    online_campuses[teacher] секретарём. Преподаватель проводит онлайн-пару с этой
    площадки; время занятия занято, поездки до и после неё проверяются. Онлайн
    рассматривается как запасной вариант при недопустимости очной площадки,
    а не как дополнительная свободная переменная оптимизации всех маршрутов.
13. Повышение лимита требует явного cap_overrides[teacher] и применяется на
    RAISE_CAP. Никакого автоматического неограниченного повышения нет.
14. Ручное назначение допускает кандидата вне автоматического пула, но сохраняет
    жёсткие запреты. Произвольный обход кафедры, красного статуса, отказа,
    компетенции или конфликта времени не реализован. Для исключений истории,
    лимита и онлайн есть отдельное обоснованное разрешение секретаря.
15. full_day разрешён даже для одной пары: исходник формулирует нежелательность,
    но не минимальную длину блока. Бонус за несколько пар подряд не добавлен.

Формат данных
-------------

Полный рабочий образец — examples/scenario.json. Верхний уровень:
data, request, необязательный policy. Ключи справочников — устойчивые коды.

data.teachers содержит name, positions, daily_cap, competences, campus_weights,
traffic. positions задаёт department и необязательные start/end в YYYY-MM-DD;
границы включительны. Дополнительные поля степени, звания, должности, факультета,
стажа и ставки можно хранить в этих записях; на ограничения они пока не влияют.
Компетенции: priority, ready, prepare, refuse; коэффициент priority от 0 до 1.
Светофор: ключ YYYY-MM-DD/номер_пары, значение green/yellow/red.

data.disciplines содержит related_groups — список кодов групп смежности.
data.slots: строковый номер → start/end HH:MM, без пересечений и перехода полуночи.
data.lessons: teacher, discipline, day, slot, group, campus либо room;
дополнительно kind и online_allowed. Реальные занятия привязаны к датам.
data.rooms и data.groups хранят справочники аудиторий и групп. Замена наследует
аудиторию и группу исходной пары, новые аудитории алгоритм не подбирает.
data.travel — направленная вложенная матрица минут; время внутри площадки 0.
data.history: id, teacher, discipline, group, day, score (0…5).

request: id, initiator, department, day, lesson_ids, psz, deadline,
timeout_minutes, mode, comments, materials. Уровни psz: general, related,
disciplinary. Одна заявка — один день; несколько дней — отдельные заявки
с общим episode_id. Срок поиска не позже начала первой выбранной пары.
Время событий ISO 8601 с часовым поясом; timezone расписания по умолчанию
Europe/Moscow. Materials — ссылки/пути; библиотека их не скачивает и не открывает.

Архитектура и внедрение
----------------------

model.py — данные и валидация; flow.py — поток; planner.py — ограничения,
стоимость, оптимизация и рейтинг; service.py — процесс и SQLite; __main__.py — CLI.
Каждая операция Service выполняется в BEGIN IMMEDIATE и записывает состояние
и аудит одной транзакцией. Два подключения не смогут одновременно назначить
разных замещающих на одну пару. Для каждого потока исполнения создавайте своё
подключение Service. Межзаявочные резервы и принятые замены видны в одной базе.

Состояние хранится одним JSON-снимком в таблице state; аудит — отдельными строками
audit. Такой формат удобен для самостоятельного алгоритмического прототипа,
но не рассчитан на высокую нагрузку крупной организации. Следующий этап внедрения:
нормализованные таблицы, API с аутентификацией, интерфейс секретаря, импорт живого
расписания, фоновые задания и отдельный обработчик outbox с повторными попытками.

Outbox содержит задания на уведомления, расписание и материалы. Письма и сообщения
внешним адресатам не отправляются. Доставка и отметки sent/failed требуют адаптера.
Лента Service.message() сохраняется без уведомлений. Вопрос инициатору по email
и реальные звонки находятся вне этой реализации.

Служебная записка, передача на оформление, отмена уже подтверждённой замены,
интерфейс администратора справочников и промышленный HTTP-сервис в текущий объём
не входят. Метод manual_assign() требует, чтобы секретарь уже получил согласие
преподавателя вне системы и указал обоснование.

Проверка
--------

Тесты проверяют ограничения, эскалацию, обе стороны переезда, онлайн, срок
исторического запрета, рейтинг без жадного тупика, пакетные переходы, таймауты,
отказы, полное подтверждение, ручное выделение, роли, сохранение после рестарта
и гонку принятия через два независимых подключения SQLite. Оптимизатор также
сравнивается с полным перебором на 100 воспроизводимых малых случайных задачах
с отрицательными стоимостями, лимитами и конфликтами перемещений.
